## 项目定位

想在 QQ 群里养一个「活的」AI:它有固定人格、记得聊过什么、知道什么时候该接话什么时候该潜水,而不是一个随叫随到的问答机器人。qq-bridge 做的事就是把 QQ 消息桥接进本地运行的 DeepSeek Harness(DSH)持久会话,再把 AI 的回复发回 QQ——双向、常驻、低延迟。

## 原项目与改动

原项目是开源的 [AI Companion Kit](https://github.com/pinganbbOvO/ai-companion-kit)(MIT):一套「给你的 AI 一副身体」的教程与组件包——从 15 分钟跑起来的快速开始,到《从零搭一只小鲸鱼》的完整教程,配套 companion、own-life、phone-mcp、qzone 等一系列组件,并给出一个可直接运行的桥接基线(单一 bridge.js 主程序,约 600KB,含 QQ↔DSH 双向转发、白名单、角色注入、MCP 工具面)。

我的版本(v0.2.1-r1)在原基线上做了四个方向的深度改造:

- **协议适配与自愈**:适配 DSH 2.0.18 的 Cookie 鉴权与 remote.mux 事件流(session/follow、投影基线、inbox 队列逐项对齐);SnowLuma 换账号后 HTTP/WS 双 token 自动发现与自愈;读接口全部加 WS 失败走 HTTP 的兜底,网关半瘫时收发不受影响
- **安全加固**:群聊内容按不可信输入对待——会话级令牌 + 常数时间比较、出站文本敏感信息审计、精确令牌名单与启发式正则双闸脱敏、state 目录 ACL 收紧(Windows icacls)、preset 清单校验失败拒绝建会话(fail-closed,绝不回退到带本地工具的默认 preset)、出站抓取全量 SSRF 防护(DNS 全结果校验、禁内网、逐跳重定向重校验)
- **长跑韧性**:DSH/SnowLuma 断线消息入队、恢复后按序补投(失败逐条放回、传输层失败可安全重试);状态文件读坏即 .corrupt 隔离 + 只读降级,绝不拿空状态覆盖原文件;单实例锁区分「真·已有实例」与「端口被占」(exit 2/exit 3,守护脚本据此决定放弃还是重试);日志按字节轮转、写失败计数进心跳
- **仿真细节**:唤醒调度器(条件触发/合批窗口/分钟与小时双限频,超限延后重试不丢唤醒)、真人感发送(分条/随机间隔/长间隔概率/双额度硬限流)、沉睡前观察窗口、时间感注入、表情包体系(收藏同步/抽帧拼图/斗图策略)、语音(ffmpeg 音量归一)、黑话学习(提取→联网考究→人工确认)、按人一本账的长期记忆、token 账本计价与日预算软上限

当前代码约 2.24 万行(src),配套 96 个测试与工具脚本,其中 45 个组成离线回归套件 `test:audit`。

## 主要功能

- 二代仿真模式(reserved2):AI 通过 MCP 工具自行决定接话或收尾,支持常驻在线(每消息唤醒)与潜水/有限睡眠两种形态
- 多模态:图片/表情/动图(抽帧拼成多格图)/语音/合并转发的读取与发送
- 群聊黑话学习:自动提取候选词,联网考究后写入注入提示词的黑话表,控制台人工确认
- 长期记忆:按人一本账 + 跨会话聊天流水,私聊群聊认得同一个人
- 费用护栏:按 token 账本折算计费,日预算软上限 + 0 点日切恢复 + 管理员日报
- 运行观测:5 分钟心跳(内存/队列/句柄/日志写失败)、运行态快照 API、每小时采样

## 技术栈

Node.js(ESM,>=22.13)/ SnowLuma SDK(OneBot v11 over WebSocket)/ DSH 2.0.18 Web API(Cookie 鉴权 + remote.mux 事件流)/ MCP stdio 服务(zod 参数校验:消息、网关状态、安全联网搜索)/ ffmpeg(语音与动图处理)/ Windows icacls(state 目录 ACL)/ Git Bash + 计划任务(自启与守护)

## 制作过程

**第一步:照教程跑通基线。** 从 15 分钟快速开始入手,起 SnowLuma 网关、连 DSH、跑通双向收发,再按《从零搭一只小鲸鱼》把完整实现铺开。这一阶段的关键决策是「先把链路跑通,再谈仿真」——每个后续功能都挂在真实收发的骨架上。

**第二步:从「问答」到「群友」。** 给桥接装上唤醒调度:哪些条件叫醒 AI(@/名字/关键词/提问/拍一拍/概率)、多条消息合并成一个唤醒(合批窗口)、每分钟/每小时唤醒配额(超限延后重试而不是丢弃)。最难的坑是**回合状态丢失**:DSH 事件流重连后 turn 结束信号可能永远不来,会话就「永久判忙」——QQ 上表现为它突然不理人了。解法是租约制(超过 15 分钟强制解除)+ 繁忙期间暂存唤醒原因、回合结束补发 + 传输层失败识别,只有「请求根本没送达」才允许重投。另一个坑是唤醒投递失败静默丢——现在会进补投队列,恢复后自动补。

**第三步:多模态与记忆。** 表情包、语音、动图陆续接入时踩了两个上游限制:DSH 的 MCP 图片入口用正则校验 base64,≥3.2MiB 必然炸栈,于是桥接侧先做归一化(缩图/压质量);DSH 把 GIF 一律压成第一帧,动图对模型「失明」,于是用 ffmpeg 抽帧拼成多格图(实测 4.8MB/200 帧 → 92KB/269ms)。记忆走「按人一本账 + 跨会话流水」,并立了条铁律:群聊绝不带入任何私聊来源,防止 AI 在群里转述私聊内容。

**第四步:安全是被现实逼出来的。** 当群友能通过对话诱导 AI 调用发送工具时,prompt injection 就不是理论问题了。逐步加了:会话级令牌(每个 QQ 会话一个,AI 工具凭令牌只能动自己会话)、出站文本审计(本机路径/凭据特征拦截)、精确令牌脱敏名单(32 位 hex 裸令牌不匹配任何正则,只能靠名单)、发送前权限再校验(排队期间权限变了就放弃发送)、state 目录 ACL 收紧。ACL 这步还踩过 icacls 的坑——(OI)(CI) 目录标志套到 /T 展开的文件上会失败,而 /inheritance:r 已摘掉继承,净结果是子文件权限被清空;修复过程中的教训是:回读自检必须排除 DSH 沙箱的 Low 完整性标签行,否则会把「已收紧」误判成「未收紧」反复执行破坏操作。

**第五步:长跑验收。** 机器人不是跑起来就算完:24~72 小时挂着,每小时采样内存/句柄/队列;注入故障(杀进程看守护 5 秒内重拉、占 3100 端口看 exit 3 重试循环、故意写坏状态文件看隔离与恢复);回归套件从十几个脚本长到 45 个。最近又做了一轮 2.5 万行级全量代码审查,修掉 2 个 P1(等待工具漏消息窗口、关键词正则注入隐患)和 15 个 P2,套件保持 43/45(2 个失败为环境缺项)。全绿之后才敢让它挂着不管。
